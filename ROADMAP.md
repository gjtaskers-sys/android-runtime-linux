# Project roadmap

Android Runtime for Linux is an experimental project exploring Android applications in native Linux desktop windows. This roadmap describes the state of the software, the work needed to reach the goal, and useful entry points for contributors. Milestones are ordered by technical dependency; no dates are promised.

## Project status at a glance

| Area | Status | What the evidence shows |
|---|---|---|
| Rust CLI and APK inspection | **Verified locally** | Workspace builds and tests pass; APK inspection and install/launch were exercised through a development Android emulator. |
| Host-side X11 display | **Verified with synthetic frames** | Eight changing frames are acknowledged, pixel samples are read back and checked, and socket/window lifecycle tests pass. |
| Rootfs tooling | **Fixture-tested** | Validation, safe assembly, metadata-preserving packaging, and preflight checks pass against test fixtures. |
| Android boot in LXC | **Not yet demonstrated** | No project Android image has yet been shown booting through Android service readiness on the target host. |
| Real Android graphics in X11 | **Not yet demonstrated** | The verified X11 source is synthetic. The Composer3/DMA-BUF integration still needs an actual built Android image and buffer-format validation. |
| Production security and packaging | **Not yet ready** | Isolation, install/upgrade/recovery, supported-host policy, and redistribution review remain open. |

## Priority 1 — Boot a candidate Android image in LXC

**Goal:** Demonstrate a repeatable Android userspace boot using the project's container configuration on a documented Debian-family host.

The project needs a candidate Android root filesystem built from pinned source metadata. Most contributors do not need to build AOSP; this step is suitable for contributors with access to a sufficiently capable build machine or a legally redistributable image with clear provenance.

**Evidence required to mark this complete:**

- The artifact includes a checksum, source manifest/revision, build metadata, and validation results.
- The host distribution, kernel, LXC version, Binder configuration, and privilege model are recorded.
- Android `init`, `servicemanager`, `zygote`, `system_server`, and PackageManager reach a healthy state.
- Stop/start behavior and persistent `/data` behavior are tested.
- An APK installs and launches inside the container.

**Useful contributions:** rootfs build validation, LXC configuration review, Binder/kernel compatibility reports, service-readiness tests, and reproducible image handoff instructions.

## Priority 2 — Display real Android frames in X11

**Goal:** Replace the synthetic frame source with actual frames generated by Android's SurfaceFlinger/Composer3 path.

This requires validation against the real allocator/exporter rather than relying on synthetic buffers. Format, modifier, planes, file descriptors, offsets, strides, acquire fences, DMA-BUF CPU-access synchronization, and buffer lifetime must agree end to end. The first implementation should retain a conservative supported-format copy path before attempting zero-copy rendering.

**Evidence required to mark this complete:** Android boot UI or home UI appears in the X11 window, followed by a real application such as 2048, with correct pixels across repeated start/stop, resize, rotation, timeout, and disconnect tests.

**Useful contributions:** Composer3/HWC expertise, minigbm/Gralloc buffer inspection, DMA-BUF/fence review, protocol robustness tests, and display-backend testing.

## Priority 3 — Input and application lifecycle

**Goal:** Make the displayed Android session usable as a desktop application rather than a view-only window.

Areas include mouse/touch input, keyboard events, Back/Home/Overview, text input/IME, scaling, resize/rotation, orderly stop/restart, and clear diagnostics. Clipboard, shared folders, and audio need explicit permission and lifecycle designs.

**Useful contributions:** input mapping prototypes, IME integration research, resize/rotation tests, lifecycle failure reports, and UX proposals grounded in the current architecture.

## Priority 4 — Hardware support and performance

**Goal:** Define a small, tested host matrix and optimize only after the CPU-copy path is correct.

Start with a software-rendering baseline and a tested fallback. Validate Mesa/minigbm and DMA-BUF/EGL import on specific hardware before making acceleration claims. Publish measurements and exact test environments rather than inferred performance estimates.

**Useful contributions:** hardware/kernel compatibility reports, repeatable performance tests, buffer-import prototypes, and distribution-specific build fixes.

## Priority 5 — Security, distribution, and stabilization

**Goal:** Establish safe installation, operation, upgrade, and recovery behavior before a stable release is considered.

Required work includes LXC confinement, host mounts and device exposure, Binder/GPU access policy, AppArmor/seccomp, ADB configuration, APK threat modeling, crash recovery, disk-full behavior, package lifecycle, third-party notices, image provenance, checksums, and reproducible release metadata.

**Useful contributions:** threat-model review, security testing, package/recovery tests, license/provenance review, and installation experience reports.

## How to contribute now

You can help without compiling Android:

- Run the Rust, frame-validation, DMA-BUF synchronization, fence, and X11 smoke tests; report failures with sanitized commands and logs.
- Improve test coverage, error messages, CI, packaging hygiene, and documentation.
- Review the frame protocol and propose test cases for malformed messages, timeouts, and lifecycle races.
- Reproduce host/kernel compatibility results and document exact versions.
- Review the proposed container security model and flag assumptions that need proof.

A full AOSP build or Android rootfs is most useful for Priority 1 and Priority 2, but it is not a prerequisite for contributing to other areas. Read [`CONTRIBUTING.md`](CONTRIBUTING.md) before opening an issue or pull request.

## Release criteria

- **Experimental source preview:** host-side functionality and limitations are documented; no claim is made that the custom Android container or real-frame graphics path works end to end.
- **Alpha runtime:** requires repeatable LXC boot, real Android frames displayed in X11, documented app lifecycle tests, and a tested installation path.
- **Stable release:** additionally requires a reviewed security model, supported host matrix, upgrade/recovery coverage, provenance/licensing review, and published compatibility results.

The project's status should only advance when the corresponding evidence is available in tests or reproducible reports.
